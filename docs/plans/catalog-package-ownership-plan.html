Starmap catalog package ownership refactor

Status: active.
Owner: this plan. Created: 2026-08-12.
Starmap baseline: main@42f1b4c6763084cc0ae7b2ced413de4d765cd9ef.
Proof root: docs/plans/proof/catalog-package-ownership/.
Next action: execute CPO8.1. Publish and independently verify immutable Starport v1.0.4 from exact current main.

Outcome

Starmap exposes one coherent catalog package tree. pkg/catalogs owns catalog values, immutable generations, and catalog codecs. Its evidence and projection leaves own neutral data contracts. Its storage, artifact, and remote children own separate behaviors. Starport consumes one immutable Starmap release. No old-path wrapper, duplicate codec, or vague metadata package remains.

Progress

The status ledger is the progress source of truth.

Architecture

A → B means that package A imports package B. Component names stay stable across both views.

Scope

Owns: the five target child packages, required type moves, and current Starmap callers. It also owns generated API docs, migration guidance, consumer fixtures, two migrations, and their releases.

Does not own: a pkg/catalogs rename or removal of pkg. A future Starmap public-API plan owns those changes. Embedding applications own new storage adapters. A future schema plan owns wire or persisted schema changes. A future provider-catalog plan owns provider and model behavior. A separate approved package plan owns unrelated cleanup.

Non-goals: old-path wrappers, removed-path aliases, duplicate codecs, new dependencies, new protocols, model behavior changes, or edits to historical evidence.

Audit evidence

  • The baseline has 31 direct Starmap import relationships across the four old packages. Starport has eight affected imports.
  • catalogstore.Generation appears in 37 files. Artifact and remote depend on storage only to exchange that value.
  • The storage encoder delegates to catalogs.EncodeCatalogPayload. The storage package owns the inverse decoder.
  • Projection results have three public consumers: synchronization, release import, and rollback.
  • The six focused package suites passed on 2026-08-12. pkg/catalogmeta reported no test files.
  • GitHub reported no open Starmap or Starport pull request. The release queries found no Starmap v0.5.0 or Starport v1.0.4 tag.
  • The design uses client-readable selectors and hierarchical packages from Go package naming and Go module layout.

Rejected designs

  • Rename catalogs to catalog: it adds broad churn without an ownership repair. Reopen under D1.
  • Keep old-path wrappers: they preserve duplicate public authority before launch. Reopen only after a public compatibility commitment.
  • Use catalogs/metadata: metadata does not name one contract. Reopen if a typed, bounded metadata concept emerges.
  • Put projection in pkg/sync: import, rollback, and synchronization share the result. Reopen under D4.
  • Move directories only: storage would still own Generation and decode. Reopen only if D3 changes.

Invariants

  1. Current source, generated docs, examples, and normative docs contain no old import path.
  2. docs/MIGRATING_TO_V0.5.md, CHANGELOG.md, reviews, and archived evidence may name old paths as history.
  3. Artifact and remote import catalog values. They never import storage.
  4. The low-level catalogs/remote protocol and the top-level reactive remote package remain separate.
  5. Fixed generation inputs keep identical payload, manifest, archive, statement, and checksum bytes.
  6. This refactor adds no module, provider behavior, schema, protocol, or arbitrary budget.
  7. All branches and pull requests target main. No task uses master.
  8. All Go checks use normal scheduling. No task sets GOFLAGS=-p.
