Outcome

Starmap publishes and embeds the Starmap public catalog. One connected runtime composes the embedded catalog, a selected upstream catalog, and operator observations into an effective catalog. Starport consumes that catalog locally or from a shared enterprise Starmap server.

Progress

The status ledger supplies progress.

Architecture

Scope

Owns: publisher credentials and cadence, catalog names, the public channel, GitHub verification, and catalog-source contracts. The plan also owns connected runtimes, application defaults, source cascading, Starport adoption, the console catalog surface, migration and topology guidance, proof, and releases.

Does not own: provider inference credentials, provider account creation, a managed AgentStation Starmap deployment, or enterprise network and storage provisioning.

Non-goals: do not change provider fact authority without an owner decision. Do not expose secrets or trust mutable tags. Do not require GitHub CLI in a Go consumer.

Invariants

Security and trust

  1. No secret value enters Git, logs, plans, proof files, or replies.
  2. The workflow exposes provider credentials only to its refresh step.
  3. The mutable channel can select only an immutable verified catalog release.
  4. Every activation verifies publisher identity, bytes, schema, and generation order.
  5. A failed source retains last-known-good state and reports degradation.

Runtime behavior

  1. A configured enterprise source causes no undeclared public GitHub fallback.
  2. The low-level catalog client remains safe for deterministic offline use.
  3. Starport validates a complete runtime candidate before acceptance.
  4. Existing catalog releases remain immutable and readable.
  5. Each background lifecycle has one owner and a bounded shutdown.
  6. One runtime retains all input layers and owns effective catalog publication.

Acquisition behavior

  1. A missing catalog-acquisition credential is neutral and causes no provider request.
  2. Provider failures retain unrelated provider observations and effective facts.
  3. A progressing bounded transfer is not canceled by an arbitrary elapsed-time default.
  4. Automatic work uses stable fleet phases, retry not-before, admission control, and one owner for shared state.
  5. A transfer is one finite HTTP body with a maximum duration, and no stage waits without a bound.
  6. Catalog-acquisition credentials come only from the deployment lookup, never from the inference keyring.
